# 工具运行状态展示维护文档

> 状态：已实现，持续维护
>
> 初版日期：2026-10-09
>
> 维护要求：凡新增、移除或修改接入运行状态展示的工具，都必须同步更新本文第 4 节和第 8 节。

## 1. 目的

部分工具执行时间较长，如果前端始终只展示统一的加载动画，用户无法判断任务是否仍在运行。运行状态展示用于把工具执行过程转换为简短、可理解的进度信息，例如：

```text
正在加载处理规范
处理规范已加载
```

该能力只展示过程状态，不暴露工具参数、返回内容、文件路径、对象存储地址或其他内部实现信息。

## 2. 整体流程

```text
模型发起工具调用
    -> 工具包装器发送 started 事件
    -> 执行原始工具
    -> 包装器发送 finished 或 failed 事件
    -> OpenAPI SSE 输出 conversation.activity
    -> Chat SDK 转换为临时 assistant 文本消息
    -> 相同 activity_id 的状态在同一气泡中更新
```

核心实现位置：

| 层级 | 文件 | 职责 |
| --- | --- | --- |
| 工具包装 | `backend/domain/agent/singleagent/internal/agentflow/tool_activity.go` | 在原始工具调用前后发送状态事件 |
| Skill 工具注册 | `backend/domain/agent/singleagent/internal/agentflow/node_tool_skill.go` | 配置 Skill 工具的状态文案 |
| 文件工具注册 | `backend/domain/agent/singleagent/internal/agentflow/node_tool_file.go` | 配置文件工具的状态文案 |
| Agent Run 转发 | `backend/domain/conversation/agentrun/internal/singleagent_run.go` | 补充会话信息并转发 Activity |
| OpenAPI SSE | `backend/application/conversation/openapi_agent_run.go` | 输出 `conversation.activity` |
| SDK 事件解析 | `frontend/packages/studio/open-platform/open-chat/src/components/studio-open-chat/provider/coz-sdk/api-adapter/message/message-parser.ts` | 识别 Activity SSE 事件 |
| SDK 消息转换 | `frontend/packages/studio/open-platform/open-chat/src/components/studio-open-chat/provider/coz-sdk/api-adapter/message/message-activity.ts` | 转换为可更新的临时消息 |
| 流式消息合并 | `frontend/packages/common/chat-area/chat-core/src/message/chunk-processor.ts` | 用新阶段替换同一 Activity 的旧状态 |

## 3. 事件约定

SSE 事件类型：

```text
conversation.activity
```

事件数据包含以下字段：

| 字段 | 说明 |
| --- | --- |
| `activity_id` | 单次工具调用的唯一标识，同一调用各阶段保持不变 |
| `tool_name` | 工具名称 |
| `phase` | `started`、`finished` 或 `failed` |
| `text` | 面向用户展示的简短状态文案 |
| `conversation_id` | 会话 ID |
| `chat_id` | 本轮运行 ID |
| `bot_id` | Agent ID |
| `section_id` | 会话 Section ID |
| `created_at` | 事件产生时间 |

前端展示规则：

| 阶段 | 前缀 | 消息状态 |
| --- | --- | --- |
| `started` | `●` | 未完成，可被后续阶段更新 |
| `finished` | `✓` | 已完成，替换同一 `activity_id` 的 started 消息 |
| `failed` | `✕` | 已完成，替换同一 `activity_id` 的 started 消息 |

Activity 使用独立的消息索引，不参与 Coze 原有 `function_call` 与 `tool_response` 的序号配对。

## 4. 已接入工具清单

| 工具 | 用途 | started 文案 | finished 文案 | failed 文案 |
| --- | --- | --- | --- | --- |
| `skill_read` | 读取 Skill 的完整说明 | 正在加载处理规范 | 处理规范已加载 | 处理规范加载失败 |
| `skill_file_read` | 读取 Skill 内的脚本或参考文件 | 正在读取参考资料 | 参考资料已读取 | 参考资料读取失败 |
| `script_run` | 在 Skill Workspace 中执行脚本 | 正在执行处理任务 | 处理任务已结束 | 处理任务执行失败 |
| `file_search` | 检索和解析会话历史附件 | 正在检索历史附件 | 历史附件检索已结束 | 历史附件检索失败 |
| `file_download` | 将会话附件下载到 Skill Workspace | 正在准备附件 | 附件已准备 | 附件准备失败 |
| `file_upload` | 上传最终产物并生成下载文件卡片 | 正在准备下载文件 | 下载文件已准备 | 下载文件准备失败 |

## 5. 持久化与刷新行为

Activity 是仅用于实时展示的过程事件，目前不写入消息表：

- 当前对话流中可以看到状态变化。
- 刷新页面后，状态消息会消失。
- 用户消息、模型最终回答和文件卡片仍按原逻辑持久化。
- Activity 不会进入后续轮次的大模型上下文，避免过程文案干扰模型推理。

如果未来需要刷新后保留状态，应采用独立运行轨迹数据或独立消息类型，并在构造模型历史时明确过滤；不要直接写成普通 assistant 回答。

## 6. 安全与文案规则

状态文案必须满足以下要求：

1. 只描述用户可以理解的动作，不展示内部工具名。
2. 不包含工具输入参数或原始输出。
3. 不包含本地路径、Workspace 路径、对象存储 Key、签名 URL 或 Token。
4. 不包含文件正文、图片 Base64、脚本源码或异常堆栈。
5. 文案应简短稳定，避免模型或工具动态生成状态文本。
6. `finished` 应描述“调用已结束”，除非工具能可靠判断业务结果，否则不要表述为“处理成功”。

## 7. 当前语义边界

`withToolActivity` 依据原始工具调用返回的 Go `error` 判断阶段：

- `error == nil`：发送 `finished`。
- `error != nil`：发送 `failed`。

`file_search`、`file_download`、`file_upload` 在 Activity 包装器外层使用 Eino 错误恢复包装器。文件工具返回 error 时，Activity 仍会发送 `failed`，但 error 随后会被转换为不含内部路径和堆栈的模型可读结果，使 Agent 可以解释问题、调整参数或提示用户重新上传，而不会以 `NodeRunError` 终止整轮对话。

部分现有工具为了避免中断 Agent 流程，会把业务失败信息作为普通字符串返回，同时返回 `nil` error。此时 Activity 会显示 `finished`，表示“工具调用已经结束”，不代表业务操作一定成功；模型仍会从工具返回文本中读取具体失败信息。

## 8. 新工具接入检查清单

新增工具运行状态时，必须完成以下事项：

1. 使用 `withToolActivity` 包装原始 `tool.InvokableTool`。
2. `ToolName` 与模型可见的工具名称完全一致。
3. 配置 `RunningText`、`FinishedText`、`FailedText`。
4. 检查文案符合第 6 节的安全要求。
5. 验证 started 与结束事件使用相同 `activity_id`。
6. 验证成功路径显示 `started -> finished`，且只保留一条状态消息。
7. 验证异常路径显示 `started -> failed`。
8. 验证多个工具连续调用时按照实际时序展示。
9. 验证最终回答、文件卡片和流式结束事件不受影响。
10. 更新本文第 4 节工具清单，并在第 9 节追加变更记录。

建议同时增加包装器单元测试；如果修改前端事件或消息合并逻辑，还应增加 Chat Core 与 Open Chat 的对应测试。
