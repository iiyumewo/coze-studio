# Coze Run 用量扣费通知过渡方案

> 状态：方案已确认，等待业务后端提供扣费接口后开始开发
>
> 记录日期：2026-09-16
>
> 方案性质：过渡方案，未来由业务后端代理 Coze 接口后计划移除

## 1. 背景与目标

当前业务前端直接接入 Coze Chat SDK。每一轮对话都会在 Coze 中产生一条 Run 记录，并在执行结束时保存该轮实际产生的 Token 用量。

由于业务后端的 Coze 接口代理尚未完成，为了尽快接入权益扣减，当前版本暂时由 Coze 在单轮执行结束后主动调用公司业务后端的扣费接口。

本方案只解决以下问题：

- 将单轮 Run 的实际用量通知给业务后端。
- 由业务后端定位用户并扣减余额。
- 记录每个 Run 的通知结果，供人工查账。
- 扣费接口异常不能影响正常聊天结果。

本方案不把余额、权益规则和业务统计能力迁入 Coze。

## 2. 长期方向与当前取舍

长期目标仍然是：

```text
业务前端
    ↓
业务后端代理层
    ↓
Coze
```

届时业务后端可以在代理 Coze 请求和响应的过程中自然取得用户身份、Run 标识和用量，并在业务系统内完成扣费。Coze 恢复为纯粹的 Agent 执行引擎，不再主动调用业务扣费接口。

当前为了缩短工期，临时采用：

```text
业务前端直接调用 Coze
    ↓
Coze 完成单轮 Run
    ↓
Coze 主动调用业务后端扣费接口
```

因此，本次新增的通知表和通知代码必须保持独立，避免把业务计费逻辑扩散到 Coze 的核心执行模型中，确保未来可以整体删除。

## 3. 系统职责

### 3.1 Coze 负责

- 执行 Agent、模型和工具调用。
- 保存每一轮 Run 的最终状态和实际用量。
- 在符合扣费条件时调用业务后端扣费接口。
- 单独记录本次通知是待调用、成功还是失败。

### 3.2 业务后端负责

- 根据业务用户 ID 定位具体用户、所属租户和权益账户。
- 以 Run ID 作为唯一业务键，防止同一轮重复扣费。
- 保存最终消费流水。
- 扣减用户或租户余额。
- 承担后续的用户、租户、时间段等用量统计。

### 3.3 明确不做

- Coze 不维护用户余额。
- Coze 不维护租户权益规则。
- Coze 不新增 conversation、用户或租户维度的用量汇总统计表。
- 当前版本不自动重试失败的扣费通知。
- 当前版本不做失败补偿任务。
- 当前版本的 Coze 到业务后端内网调用不增加接口鉴权。

## 4. 用户身份传递

当前业务前端传给 Chat SDK 的用户信息为：

```json
{
  "id": "tenantId:userId",
  "nickname": "用户显示名称",
  "url": ""
}
```

Chat SDK 发起对话请求时，只会把其中的 `id` 作为 `user_id` 发送给 Coze。Coze 会把该值以字符串形式保存到每一条 Run 记录的 `user_id` 字段中。

因此，Run 记录中可直接获得：

- Run ID。
- Conversation ID。
- 业务用户标识 `user_id`。
- Run 状态。
- 输入 Token、输出 Token 和总 Token。

昵称和头像只用于前端显示，不会完整保存在 Run 记录中，也不是扣费所需信息。

公司业务系统中的用户 ID 可以唯一定位具体用户，因此业务后端可以根据收到的 `user_id` 找到用户、租户和权益账户。当前继续使用 `tenantId:userId` 也没有问题；是否简化成单独的全局唯一 `userId`，可以在接口确定时决定。

## 5. 扣费触发规则

扣费判断以 Run 最终保存的实际用量为准，而不是仅以状态为准。

| Run 最终状态 | 是否存在实际用量 | 是否调用扣费接口 |
| --- | --- | --- |
| `completed` | 有 | 是 |
| `completed` | 无 | 否 |
| `failed` | 有 | 是 |
| `failed` | 无 | 否 |
| `cancelled` | 有 | 是 |
| `cancelled` | 无 | 否 |

核心原则：

```text
有实际用量就扣费，没有实际用量就不扣费。
```

失败和取消不代表没有成本。只要模型或其他计费用量已经实际产生，就需要通知业务后端扣减余额，避免业务实际消耗大于扣减金额。

## 6. Run 真正结束的定义

Run 记录在一轮对话开始时就会创建，之后进入执行中状态。用户点击取消时，Run 记录已经存在。

“用户点击取消”只代表收到取消请求，不应直接等同于本轮已经完成结算。正确的扣费时机是：

```text
Run 开始
    ↓
创建 Run 记录
    ↓
模型和工具执行
    ↓
执行真正退出并确定最终状态与最终用量
    ↓
保存 Run 最终结果
    ↓
进入扣费通知流程
```

实现时需要为 `completed`、`failed` 和 `cancelled` 找到统一的最终收尾入口，保证同一个 Run 只确定一次最终状态，只产生一次通知记录。

如果取消后底层模型没有返回用量，Coze 无法推算真实消耗，本版本按“无实际用量记录则不扣费”处理。

## 7. 通知结果表

Coze 侧不建设用量汇总统计表，但需要单独建设一张临时的扣费通知结果表。

这张表不是业务账本，也不是统计表。它只回答：

```text
某个 Run 是否调用过业务扣费接口，以及调用结果是什么。
```

### 7.1 一条 Run 一条记录

`run_id` 应设置为唯一键。同一个 Run 不存在多条通知结果记录。

建议字段如下，最终名称可在开发时结合仓库规范确定：

| 字段 | 含义 |
| --- | --- |
| `run_id` | Run 唯一标识，也是业务扣费幂等键 |
| `user_id` | 业务用户标识 |
| `conversation_id` | 所属多轮会话，便于排查 |
| `run_status` | Run 最终状态 |
| `input_tokens` | 输入 Token |
| `output_tokens` | 输出 Token |
| `total_tokens` | 总 Token |
| `notification_status` | `pending`、`success` 或 `failed` |
| `http_status` | 业务接口返回的 HTTP 状态码 |
| `business_code` | HTTP 200 响应中的业务状态码 |
| `response_body` | 必要时保存精简后的响应内容，便于查账 |
| `error_message` | 超时、连接失败或解析失败等错误信息 |
| `created_at` | 通知记录创建时间 |
| `updated_at` | 最后更新时间 |

### 7.2 状态含义

- `pending`：Run 已经完成本地落库，通知记录已经创建，业务接口尚未得到最终结果。
- `success`：业务接口明确返回扣费成功，或明确返回该 Run 已经处理过。
- `failed`：HTTP 状态、业务状态码、网络请求或响应解析表明扣费没有成功。

当前版本不对 `failed` 自动重试。`pending` 和 `failed` 只用于查账与人工排查。

## 8. 完整处理流程

```text
Run 真正结束
    ↓
确定最终状态和最终用量
    ↓
保存 Run 最终记录
    ↓
没有用量：结束，不创建扣费通知
    ↓ 有用量
创建一条 pending 通知记录
    ↓
提交 Coze 本地数据
    ↓
调用公司业务后端扣费接口
    ↓
根据 HTTP 状态和业务返回码判断结果
    ↓
更新通知记录为 success 或 failed
    ↓
聊天流程保持原有结果，不因扣费接口失败而改变
```

为了减少“Run 已保存，但通知记录尚未创建时进程退出”的窗口，建议把 Run 最终状态更新和 `pending` 通知记录创建放在同一个本地数据库事务中。对外 HTTP 调用必须在本地事务提交之后执行。

无论业务扣费接口成功、失败、超时还是返回异常数据，都不能把已经完成的聊天改成失败，也不能阻止正常的流式结束事件发送给前端。

## 9. 业务扣费接口契约

业务后端接口尚未提供，以下仅作为双方对齐时的最小建议，不是最终接口定义。

### 9.1 建议请求内容

```json
{
  "run_id": "123456",
  "conversation_id": "789012",
  "user_id": "100:200",
  "run_status": "completed",
  "usage": {
    "input_tokens": 100,
    "output_tokens": 50,
    "total_tokens": 150
  }
}
```

其中：

- `run_id` 是业务后端的扣费幂等键。
- `user_id` 用于定位业务用户和租户。
- `conversation_id` 用于审计和问题排查。
- `run_status` 用于说明本轮是完成、失败还是取消。
- `usage` 是该 Run 最终保存的实际用量。

### 9.2 成功判断

不能只根据 HTTP 状态码判断成功。

当前原则为：

- HTTP 状态码不是 `200`：记为失败。
- HTTP 状态码为 `200`：继续解析业务响应码。
- 只有业务响应码明确表示扣费成功，或者明确表示该 `run_id` 已处理，才记为成功。
- HTTP 200 但业务响应码表示失败：仍记为失败。
- 响应无法解析或缺少必要字段：记为失败。

具体业务成功码、重复处理码和返回结构，需要等待业务后端接口确定。

### 9.3 业务后端幂等要求

即使当前 Coze 侧只主动调用一次，业务后端仍应以 `run_id` 建立唯一约束。

业务处理语义应为：

```text
第一次收到 run_id：写消费流水并扣减余额
再次收到相同 run_id：不重复扣费，并返回已处理结果
```

这是业务账务正确性的最后一道保护，不能依赖 Coze 侧“理论上只调用一次”。

## 10. 当前版本接受的限制

为了控制工期，当前版本明确接受以下限制：

- 不做自动重试。
- 不做定时补偿。
- 不做消息队列或 Outbox 投递 Worker。
- 内网调用暂不增加签名、服务 Token或 mTLS。
- Coze 进程在特定时间窗口异常退出时，可能留下 `pending` 记录，或出现未完成通知的 Run，需要通过查账发现并人工处理。
- 如果模型被中断且供应商没有返回 usage，本版本无法估算已产生的 Token，因此不会扣费。

这些限制是当前工期下的主动取舍，不代表长期设计。

## 11. 可移除性要求

为了未来切换到业务后端代理模式，本次实现需要满足：

- 通知结果使用独立数据表，不向核心 Run 表增加业务扣费字段。
- 扣费接口调用封装为独立模块。
- 核心执行流程只依赖一个通用的“Run 最终用量通知”边界，不直接出现余额、权益或租户计价规则。
- 配置中可以整体关闭主动通知功能。
- 删除通知模块和通知表后，不影响 Run、Conversation、消息和 usage 的原有持久化。

未来迁移顺序建议为：

```text
业务后端代理 Coze 接口上线
    ↓
确认业务代理已稳定取得并处理每轮用量
    ↓
关闭 Coze 主动扣费通知
    ↓
发布移除通知读写逻辑的版本
    ↓
确认所有实例升级完成
    ↓
删除临时通知结果表
```

## 12. 开发前待确认事项

目前没有新的业务设计疑问。开始开发前只需等待业务后端提供并确认以下接口契约：

1. 接口 URL 和 HTTP 方法。
2. 请求字段名称和数据类型。
3. HTTP 200 响应体结构。
4. 扣费成功的业务状态码。
5. `run_id` 已处理时的业务状态码和响应语义。
6. 业务错误信息字段。
7. 请求超时时间。

接口契约确定后，即可开始数据库迁移、通知模块和 Run 最终收尾接入的开发。
